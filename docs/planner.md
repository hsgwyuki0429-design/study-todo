# 自動プランナー（Jev）

毎日 03:00（JST）に、学習の記録から次の予定を組み直す仕組み。
利用者は学習して評価を入れるだけで、翌日の予定が更新されている状態を目指す。

## 何を誰が決めるか

判断を任せる範囲と、コードで固める範囲をはっきり分けてある。

| Jev（TypeSafe AI System One）へ尋ねる | コードで確定する |
|---|---|
| 履歴から見た復習の必要度（Score） | 最終実施日・回数・復習予定日 |
| 次に解くまでの望ましい間隔（Choice: 1/3/7/14/30日・unknown） | 実際に何月何日へ置くか |
| 同じ問題を繰り返すか、関連する基礎へ戻るか（Choice） | 選べる問題ID・目標の対象・関連の出どころ |
|  | 期限・学習可能時間・固定/実行中の保護・重複の防止 |
|  | 時間の集計と保存、再送の管理 |

Jev が返すのは「何日後が望ましいか」まで。
その日の枠が埋まっていれば、期限・固定予定・容量を守れる**最も近い日**へ置く。
Jev に自由な日付を書かせることはしない。

答えが `unknown` のとき、確信度が低いとき、Jev が止まっているときは、
評価履歴だけから決まる規則（`server/service/planner-policy.js`）へ戻す。
予定は止まらず、理由も説明できる形で残る。

## 走る順番

`server/service/planner-runner.js`

1. **起動の確保** … `eventId` を台帳で確保する。同じ daily は一度だけ。
   学習中は daily を延期し、手動実行ははっきり断る（従来どおり）。
2. **材料の取得** … `getPlanningContext`（14日ぶん）に加えて、学習記録・問題マスタ・
   問題どうしの関連・目標を読む。未配置と繰り越しは上限を上げて**全件**見る
   （`truncated` のまま「全部見た」と思わないため）。
3. **候補づくり** … やり残し／目標の未配置分／土台への戻し／長期復習。
   これからの日にすでに置いてある予定は動かさない（無用な入れ替えを避ける）。
4. **特徴量** … 評価履歴・回数・perfectの回数・前回からの経過日数・見積もりと出どころ。
   解答時間から「知識不足」のような原因は決めつけない。
5. **Jev へ問い合わせ** … 8件ずつまとめて、3つの独立した質問を送る。
   履歴の無い問題については尋ねない（判断する材料が無いため）。
6. **整列** … 期限 → 待たされた日数 → 優先枠 → 目標の優先順位 → 難易度の進み方 →
   必要度 → 掲載順 → 問題ID。同じ入力なら必ず同じ順になる。
7. **配分** … 秒で数えて空いている日へ置く。未設定の日には置かない。
   1問で1日の枠を超える問題は置かない。置けない分は「不足」として理由つきで残す。
8. **差分化** … 過去の分は `carryOver`、これからの分は `move`、新しい分だけ `add`。
   1タスク1問。既存の複数問題タスクとチャレンジは分割しない。
9. **検証** … `validatePlanChanges` に全変更日の `expectedRevisions` と
   `expectedContext` を渡す。自動反映では **warnings も停止条件**として扱う
   （`over_capacity` / `capacity_not_configured` / `after_deadline` / `single_item_too_long`）。
10. **反映と読み直し** … `applyTaskChanges` で一括保存し、読み直して確かめてから
    `applied` と呼ぶ。

## 安全のための決めごと

- **判断した時点と保存の時点** … `expectedContext` に `plannerSnapshotVersion`
  （目標・学習可能時間の版に加え、学習記録の件数と最新時刻）を足した。
  判断している間に記録が増えていたら、その案は保存せず作り直す。
- **再送** … `operationId` は `auto-replan-<eventId>` で固定。
  結果が分からないときは**同じ要求**をそのまま送り直す。内容を変えた要求は重ねない。
- **状態** … `pending / evaluating / validated / applied / no_change / deferred / failed`。
  Claude Routine の `triggered` は「起動を伝えた」だけで、計画の更新完了ではない。
  同じ言葉にはしていない。
- **権限** … プランナーはサーバーの中から同じサービス関数を呼ぶが、
  `actorKind: ai` の保護（完了・実行中・固定）はそのまま効く。
  学習記録を作る・直す・消す機能は渡していない。
- **秘密と送る中身** … `JEV_API_KEY` は Worker Secret にだけ置く。
  ブラウザ・同期データ・バックアップ・Git には入らない。
  外へ出るのは匿名の問題ID・評価・回数・日数・秒数だけで、
  氏名・認証情報・教材の本文は送らない。
- **障害時** … Jev が止まっても今の予定は保たれる。新しく置く必要があるときだけ、
  規則で最低限の配分をして、同じ厳しい検証を通す。
  認証の誤りは繰り返し呼ばず、設定の確認を促す。

## 学習の方針（`planner-policy.js`）

- 通常の予定は1タスク1問。
- 復習を新規学習より優先する。置ききれない分は不足として残す。
- 難易度3までを進めてから4以上へ（目標の `priority` と問題の `difficulty` は別物）。
- ◯完璧にできた が**合計2回**そろえば一旦クリア
  （目標の達成条件 `completion.mode = "count"`, `count: 2`）。
  画面の達成表示も同じ条件で判定する（`src/goals.js` を PWA とサーバーで共有）。
- クリア後も、難易度4以上の問題と、誤答を2回以上繰り返した問題は長期復習に残す。
- いちばん基本的で安定した問題の反復は減らす。

## 段階的な導入

| 段階 | `PLANNER_PROVIDER` | 何を見るか |
|---|---|---|
| 0 | `claude_routine` | これまでどおり。判断の契約と達成条件だけ先に入れる |
| 1 | `off` | 自動再計画を止めて、手動だけにする |
| 2 | `jev_shadow` | 案は作るが保存しない。判断の質と理由の妥当性を見る |
| 3 | `jev` | 制約を確かめたうえで保存する |

切り戻しは `PLANNER_PROVIDER` を戻すだけ。
実行先はイベントごとに決まるので、2つのAIが同じイベントへ同時に書くことはない。

## 費用の目安

調査時点の公開価格（入力100万トークンあたり 0.042 米ドル、出力は無料）での**概算**。
実測ではない。

| 想定 | 月間の入力トークン | Jev の推論費用 |
|---|---|---|
| 1日1回・1回20,000トークン | 600,000 | 約 0.025 米ドル |
| 1日5回・同条件 | 3,000,000 | 約 0.126 米ドル |

Cloudflare・保存・通信・将来の価格改定は含まない。
現行の保存先は1人用の Durable Object を1つ使う構成なので、
多人数での提供は認証・利用者ごとの分離・上限とあわせて別に考える。

## 設定

```sh
npx wrangler secret put JEV_API_KEY
# 任意: JEV_API_URL（既定 https://api.typesafe.ai/v1/systemone）／JEV_MODEL（既定 jev-latest）
# 実行先は wrangler.toml の [vars] PLANNER_PROVIDER
```
